# Activity History — staged deployment

Alpha only. No cloud resources or client application have been deployed for this change. Keep `COUNTER_SESSION_ENFORCEMENT` in COMPATIBILITY mode; do not enable ENFORCED.

1. Confirm the target is the shared Alpha/Beta CloudBase environment and take a current backup. Inspect its live functions and schema before making changes. Do not overwrite unrelated live changes.
2. Ensure `counter_session_history` exists. Apply `database/counter_session_history.rules.json` (deny all direct client reads and writes). Add only the missing indexes in `database/counter_session_history.indexes.json`: venue/time, event/time, staff/time, session/time, type/time, venue/type/time and venue/event/time; preserve existing indexes.
3. Download live code for `manageApplications`, `manageStaff`, `checkInGuest`, and `clientAuth`. Overlay only the changes in this commit, including the new `manageApplications/activityHistory.js` module. Incrementally deploy, download again and compare hashes/diffs. Do not repeat a write when CloudBase reports native pending; retain its task ID.
4. `clientAuth` has two Alpha repository copies: Admin and Guest. Their updated source files must match before deploying the shared cloud function. Confirm compatibility with published Alpha/Beta clients before each upload. Do not deploy if compatibility cannot be established.
5. Publish Admin (and Guest only if a changed client is required) later, separately and only with owner permission. Manually check admin-only read access, light/dark UI, venue/event/time navigation, Shanghai overnight events, search/pagination, session summaries, guest switches and QR/manual attendance. Do not reconstruct events before the deployment date.

Limitations: paid-ticket history needs a separate payment-function change and is not collected here. Standalone cancellations or registration-type edits, when not implemented as server operations, cannot be logged. No Counter remove-registration action exists in the current function routes, so its summary remains zero until such an operation is introduced. The deleted-event listing reads at most 1,000 deletion records; for larger histories a dedicated indexed materialized event catalogue will be needed. Session summaries count at most 1,000 events and flag partial results. Older or unversioned clients are not subject to ENFORCED until explicitly activated.
