# Counter sessions — staged rollout (Admin Alpha)

Server switch: `COUNTER_SESSION_ENFORCEMENT=ENFORCED` activates strict checks in **manageApplications**, **checkInGuest** and **manageStaff**. An absent value or `COMPATIBILITY` leaves old published Counter clients on legacy routes; a new client carrying an invalid session is rejected. The client cannot set this switch. Never set ENFORCED before the owner authorizes it and all relevant Admin clients are published.

Before deploying any of these functions, download their live source and overlay only the changes in this commit. Deploy incrementally, download again and compare hashes. All three functions must use the same switch value; otherwise protection is incomplete. Do not overwrite other live modifications. The shared environment also serves Beta; retain COMPATIBILITY until coordinated rollout.

The session lock lives in `venues.counterSession` and authorization generation in `venues.passwordVersion`; both are server-only fields. Cloud database rules for `venues` must deny direct client writes and reads (including session hashes and password). The new `counter_session_history` collection must be created with **no client read/write/delete permissions**, granting access only to cloud functions. Rules and four minimal History lookup indexes (venue/time, event/time, staff/time, global time) are specified in `database/counter_session_history.*.json`. These are preparation artifacts, **not applied**. Provision and read back these rules before deployment; otherwise do not deploy. History stores server snapshots, not credentials. Failed-login audit entries coalesce per employee/venue/five-minute bucket. Do not create a public collection or allow the client to mutate the lock.

The work session lasts until the event ends, including Shanghai overnight events and administrator schedule changes. Heartbeat checks the session every 30 seconds; it does not enforce an inactivity timeout. Backgrounding and temporary network loss do not log out. The client stores only the session reference (never the venue password), bound to the cached staff ID, and revalidates it on the server before reopening the workspace after restart. Old clients may still log out on backgrounding until the updated Admin is published. Server-side closure/force logout/password rotation/role revocation removes or invalidates the lock; any stale server record is checked against its event and staff before denying a new login. No client upload or release is performed here.

The `wx-server-sdk` transaction on protected writes touches the venue, event, staff and target document. Password rotation, force logout, login and logout write the same venue document; role revocation writes staff and affected venue documents. A conflicting stale write rolls back instead of applying. Security events for those critical transitions are written in the same transaction; when History is unavailable the transition fails closed. Successful-login and expiry entries use deterministic document IDs; other successful transitions remove the session so repeated requests cannot duplicate their event. Failed attempts are coalesced per employee/venue/five-minute bucket. Heartbeat creates no History entry.

Limitations before ENFORCED: old published clients can still use legacy Counter calls, so exclusivity only applies to newly issued sessions. The updated Counter page no longer opens a raw `registrations` watcher; it polls the server-checked function. **Already published old clients may still read `registrations` directly if collection rules allow it.** Enabling ENFORCED does not by itself revoke direct database access: inspect existing `registrations` rules and every published Guest/Admin read path first, then plan a coordinated rules/client rollout. Git push alone does not deploy cloud functions or publish the Admin client; the owner performs both operations manually.
